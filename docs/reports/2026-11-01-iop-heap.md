# IOP heap pressure after sound initialization

## Observed failure

The wider live-immediate diagnostic still returned to the loader after sound initialization. Scratch-only dispatch tracing now identifies the transition: `adpcmMgrInit` calls the routine at `0x011576d8`, which requests `0x58000` bytes (352 KiB) through `sceSifAllocSysMemory` at `0x0010dde0`. The first allocation returns `0x001562c0`; the next returns zero. The failure branch at `0x01157768` calls `iosJumpRecoverPoint`, which transfers control through the loader recovery path. This is an intentional guest failure response, not evidence of an arbitrary scheduler stall.

The production IOP memory implementation reserves `0x00120000` through `0x001f0000` for its heap: 832 KiB. At the observed failure, 16 live allocations total 412,096 bytes. There are 439,872 free bytes in total, but the largest contiguous gap is only 269,632 bytes, below the 360,448-byte request. The allocator also uses a monotonically advancing cursor and does not reuse freed holes; repairing that alone would not make this particular second request fit the measured gaps.

## Controlled diagnostic experiment

Only the external scratch runtime changed. Its HeapBase was lowered from `0x00120000` to `0x00080000`, retaining the same 2 MiB IOP RAM and heap upper limit. The existing module loader uses HeapBase as its upper bound, so its overlap rejection remained active, with a smaller module arena. This is a partition experiment, not a production fix or an increase in physical RAM.

The diagnostic runner rebuilt successfully. A 20-second boot probe then observed three successful 352 KiB allocations, returning `0x000b62c0`, `0x0010e2c0`, and `0x001662c0`. These three buffers alone require 1,081,344 bytes, exceeding the original entire 851,968-byte heap. Execution continued beyond the previous recovery branch into graphics-related calls, including GsGetIMR and GsPutIMR. This establishes that heap partitioning blocks this diagnostic boot path. It does not establish correct rendering or gameplay.

## Validation and limits

The dispatch-tracing, heap-dump and partition variants were each rebuilt and run separately. The original-partition probes reproduced recovery after a failed allocation. A script computed the live/free/gap sizes from the allocation dump. Existing production unit-test passes remain applicable because production source did not change in this investigation; the broader Debug suite still has its previously reproduced scheduler assertion.

The experiment retains manual FILEIO/LIBSD/SG2IOPM1 injection, snapshot-derived EE addresses, and the 691-site live-immediate configuration. Normal IOP lifecycle, host audio, reliable graphics/gameplay and Xbox execution remain unverified. No executable release is claimed.

## Implementation direction

A production solution needs a deliberate policy for sharing the IOP's 2 MiB between loaded modules, thread stacks and guest allocations, with collision checks and freed-block reuse. Blindly changing HeapBase would reduce the supported module arena and could reject modules accepted by the existing implementation. <!-- coderabbit-ai-generated:v1 -->
